# Хранилище секретов — OpenBao на стенде (Р-456 B)

Поднято и доказано на стенде `<адрес-стенда>`, каталог `/srv/broker/vault`.
Это рабочие артефакты зоны deploy; секретных значений здесь нет — только
конфигурация, пути и плейсхолдеры.

## Что это и почему OpenBao

OpenBao — форк HashiCorp Vault под Apache-2.0 (ратифицировано Р-456 B как
предпочтительный). Один узел, integrated storage (raft) — внешней БД не
требует. Заменяет «секреты в `*.env`» на хранилище с ротацией и журналом
доступа. Спека: `wt-deploy-veha5/server/СЕКРЕТЫ-Vault-спека.md`.

### mlock / IPC_LOCK — требование спеки устарело

OpenBao 2.7 **убрал поддержку mlock** вовсе (upstream). Поэтому
`disable_mlock` и capability `IPC_LOCK` из спеки больше неприменимы и сняты.
Защита секретов от попадания в своп теперь — на уровне ХОСТА: отключить или
зашифровать swap. На стенде есть `/swapfile` 4G — **см. остаточные риски**.

### Распечатывание и custody (РЕШЕНИЕ ВЛАДЕЛЬЦА — ОТКРЫТО)

- Unseal-ключи (5 шт., Шамир) + root-токен лежат на стенде:
  **`/root/openbao-unseal/init.json`**, права **600 root**. Это ВНЕ
  `/srv/broker`, поэтому в ночной бэкап (`config.tar.gz` тарит только
  `/srv/broker`) ключи НЕ попадают — как и требует спека.
- **Это INTERIM-хранение на машине.** Кто и где держит ключи офлайн —
  решение владельца (открытый вопрос 2 спеки): сам ключ от хранилища должен
  жить НЕ на той же машине, иначе хранилище бессмысленно.
- **Следствие, которое надо знать:** после перезагрузки хоста OpenBao
  встаёт ЗАПЕЧАТАННЫМ (auto-unseal не настроен). Распечатать — 3 из 5 ключей.
  До распечатывания витрина/кабинет работают на fallback (базовый `.env`,
  см. ниже), то есть KYC переживает ребут, но ротация стоит до распечатывания.
- root-токен сейчас живёт в `init.json`. **Остаточный риск:** по-хорошему его
  надо отозвать после настройки и выпускать по требованию через
  `bao operator generate-root` (нужны unseal-ключи). Оставлен interim, чтобы
  не лишать штаб администрирования до постановки процесса custody.

## Доставка в сервисы — Vault Agent sidecar по AppRole

`broker-vault-agent-site` логинится по AppRole `site` (политика `kyc-read`,
только чтение `secret/data/kyc/*`) и рендерит
`/srv/broker/vault/rendered/.env.kyc` (права 0600). Обёртка витрины
`compose.sh` подключает этот файл ПОСЛЕДНИМ `--env-file` — он перекрывает
одноимённые ключи из базового `.env`.

- role_id/secret_id — в `/root/openbao-agent-site/` (600), ВНЕ `/srv/broker`
  (не в бэкапе). Остаточный риск: secret_id бессрочный (interim); в
  закалённом варианте — response-wrapping + ротация secret_id.
- **Fallback-дизайн (сознательный):** нет отрендеренного файла (OpenBao
  запечатан/недоступен) → `compose.sh` берёт значения из базового `.env`.
  OpenBao НЕ сделан единой точкой отказа витрины, пока custody unseal-ключей
  не решён. Базовый `.env` намеренно оставлен как страховка.

`admin` и `cabinet` пересозданы один раз, чтобы перейти на эту доставку;
значения идентичны прежним, поведение не изменилось. KYC-загрузка проверена
после переключения (put/get через ключ из OpenBao — успех).

## Ротация ключа без рестарта — ДОКАЗАНО (критерий Р-456 B)

Доказано на стенде на ОТДЕЛЬНОМ throwaway-ключе (путь `secret/kyc/_rotdemo`,
временный svcacct MinIO, scoped на бакет), чтобы не трогать живой ключ KYC.
Наблюдение:

1. потребитель читает ключ A из отрендеренного файла → PUT в MinIO OK;
2. в OpenBao ключ заменён на B (создан новый svcacct); Vault Agent
   **перерендерил файл за ~3 секунды** — контейнер агента НЕ перезапускался
   (`StartedAt` и `RestartCount=0` до и после совпали);
3. потребитель, перечитав файл, работает ключом B → PUT OK;
4. старый ключ A отозван в MinIO → им PUT уже FAILED, ключом B — OK.

Весь конвейер ротации — без рестарта OpenBao, агента и MinIO. После проверки
throwaway-ключ, демо-svcacct, демо-путь и тестовые объекты удалены.

### Честная граница: сами broker-admin/broker-cabinet

Образы `admin`/`cabinet` читают S3-креды из `process.env` ОДИН раз на старте
и кешируют S3-клиент (`packages/storage/src/client.ts` — отпечаток включает
`accessKeyId`). У РАБОТАЮЩЕГО контейнера `process.env` неизменен, поэтому
новый ключ он подхватит только при пересоздании (recreate), а не «на лету».
Конвейер доставки ротирует без рестарта (доказано выше); чтобы и сами
приложения подхватывали ключ без рестарта — нужен один из путей (решение
разработки/владельца):
- читать креды из отрендеренного файла через уже имеющийся seam
  `StorageEnvSource` (небольшая правка приложения), либо
- Transit (ключ не покидает хранилище) — он же вариант для Р-452.

  полностью согласован. Данные в томе зашифрованы барьером Vault. Правильнее —
  `bao operator raft snapshot` отдельным шагом бэкапа. Вынесено в долг.

## Операции

```bash
# статус
docker exec broker-vault bao status -address=http://127.0.0.1:8200
# распечатать после ребута (3 из 5 ключей, НЕ печатать значения в логи/чат)

# поднять/обновить
cd /srv/broker/vault        && docker compose up -d   # сервер
cd /srv/broker/vault/agent-site && docker compose up -d   # агент
```
