# Шина событий · кредлы и права

Какие кредлы существуют, какие права у каждого и **почему именно такие**. Права
сужены осознанно: «дать всем всё» здесь не выход, потому что шина — общая для
платформы, и продюсер не должен уметь читать чужие очереди.

Локальная шина: RabbitMQ 3.13, vhost `platform`, AMQP 5672, консоль 15672.
Пароли — в `deploy/local/.env`, в историю не попадают.

## Кредлы

| Пользователь | Тег | configure | write | read |
| --- | --- | --- | --- | --- |
| `site-web` | нет | — | `^platform\.events$` | — |
| `cabinet` | нет | `^cabinet\.terminal-projection$` | `^(cabinet\.terminal-projection\|platform\.events\.dlx)$` | `^(platform\.events\|cabinet\.terminal-projection(\.dlq)?)$` |
| `bus-admin` | administrator | `.*` | `.*` | `.*` |

## Почему у `site-web` БЫЛ `configure` и почему его больше нет

Задача говорила: кредл `site-web` выдан publish-only, это правильно и менять не
нужно. **Проверено — в строгом виде это неверно, и релей от этого падает.**

Релей вызывает `assertExchange('platform.events', 'topic', {durable:true})`
перед первой публикацией. `exchange.declare` требует `configure` на обменнике
**всегда**, даже если обменник уже существует. С пустым `configure` релей
получает тот же `403`, что и консюмер:

```
ACCESS_REFUSED - configure access to exchange 'platform.events'
                 in vhost 'platform' refused for user 'site-web'
```

Воспроизведено: сузил права до пустого `configure`, перезапустил релей — он
ушёл в цикл падений (`RestartCount=3`), событие осталось в `outbox` с
`attempts=0`, то есть отказ произошёл **выше** пер-строчной логики повторов и
даже не записался как попытка публикации.

> **Уточнено 06.10.** «Выше логики повторов» — верно, но причина была названа
> неверно: дело не в правах, а в порядке навешивания обработчиков. Отказ
> приходит событием `error` на канале, у которого ещё нет слушателя, и Node
> гасит процесс раньше, чем `catch` запишет попытку. Разобрано в
> `B-OPS-006`; воспроизводится и без всяких `403` — достаточно указать
> релею несуществующий обменник.

**Отказ отложенный, и это худшее в нём.** Пока у релея открыт канал, он не
переобъявляет обменник и работает. Сломается он только при следующем
переподключении — то есть при рестарте, разрыве сети или перезапуске брокера.
Сузь права в пятницу — узнаешь в понедельник.

Минимальное расширение было дано тогда: `configure` **только** на
`^platform\.events$`. Очередь объявить им было нельзя (проверено), прочитать
нельзя (проверено) — но обменник создать или переопределить было можно.

### Сужено 06.10 (OPS-13): `configure` снят

`REL-03` сделан: релей объявляет обменник **пассивно** (`checkExchange` вместо
`assertExchange`, `apps/relay/src/publisher.ts`). Пассивное объявление по
правилам RabbitMQ **не требует никаких прав**, и это разблокировало честный
publish-only. Права `site-web` теперь:

```
rabbitmqctl set_permissions -p platform site-web "" "^platform\.events$" ""
```

Обменник создаёт владелец шины один раз; релей его только требует и не чинит
молча.

**Проверено после сужения, каждое — попыткой** (образы пересобраны, OPS-12):

| Попытка от `site-web` | Ответ брокера |
| --- | --- |
| `exchange.declare` активно | `403` classId 40 — «configure access to exchange ... refused» |
| `exchange.declare` **пассивно** | прошло |
| `queue.declare` | `403` classId 50 — «configure access to queue ... refused» |
| `basic.consume` чужой очереди | `403` classId 60 — «read access to queue ... refused» |
| `basic.publish` в `platform.events` | прошло, подтверждено брокером |
| `checkExchange` несуществующего | `404 NOT_FOUND`, обменник **не создан** (список обменников — ноль совпадений) |

Главное — **с переподключением, а не на живом канале**: релей контура
перезапущен уже под суженными правами, после чего строка `outbox` ушла в шину
(`published_at` проставлен, `attempts = 0`, ошибок нет). Отказ, который
проявляется только при переподключении, тише отказа при старте — проверять его
надо именно так.

**Что сужение стоило:** ничего из работающего. **Что оно закрыло:** продюсер
больше не может переопределить тип или свойства общего обменника платформы.

## Почему у `cabinet` есть `write` на DLX

Не догадка, а следствие отказа. Первый набор прав я вывел из задачи —
`configure` + `write` + `read` на очередь. Консюмер упал:

```
ACCESS_REFUSED - write access to exchange 'platform.events.dlx'
                 in vhost 'platform' refused for user 'cabinet'
```

RabbitMQ проверяет права на dead-letter-обменник **в момент `queue.declare`**, а
не когда сообщение реально отбраковывается. Очередь объявляется с
`deadLetterExchange: 'platform.events.dlx'`, и объявляющий обязан иметь `write`
на этот обменник. Ровно поэтому в постановке стояло «и её DLX».

## Откуда остальные права `cabinet`

Выведены из того, что консюмер делает, а не выданы про запас:

| Вызов в `subscriber.ts` | Требует |
| --- | --- |
| `checkExchange('platform.events')` — ПАССИВНО (CON-04) | **ничего**: пассивное объявление прав не требует |
| `assertQueue('cabinet.terminal-projection', {deadLetterExchange})` | `configure` на очереди + `write` на DLX |
| `bindQueue(queue, exchange, 'terminal.#')` | `write` на очереди (назначение) + `read` на обменнике (источник) |
| `consume(queue)` | `read` на очереди |

`read` на `cabinet.terminal-projection.dlq` добавлен сверх необходимого — чтобы
разбирать отбракованные сообщения тем же кредлом. Это осознанное расширение, не
упущение.

### `configure` на `platform.events` снят 19.10 (Р-051)

Зеркальный REL-03 сделан: `CON-04` заменил `assertExchange` на `checkExchange`,
а пассивное объявление `configure` не требует. Порядок соблюдён — сначала код
в образе, потом права.

`configure` на **собственной очереди** `cabinet.terminal-projection`
**остаётся**, и это решение, а не недоделка: очередь объявляется активно
сознательно, её владелец — сам консюмер, и потерянную очередь пересоздать
больше некому. У `site-platform` закреплено тестом-растяжкой, чтобы следующий
не «дозакрыл» её ради симметрии.

Проверено попыткой и **с переподключением** — отказ, видимый только при
реконнекте, тише отказа при старте:

| Попытка кредлом `cabinet` | Результат |
| --- | --- |
| `checkExchange('platform.events')` — пассивно | получилось |
| `assertExchange('platform.events')` — активно | `403 ACCESS_REFUSED configure access to exchange 'platform.events'` |
| `assertQueue('cabinet.terminal-projection')` — своя | получилось |
| `assertQueue('cabinet.not-mine')` — чужая | `403 ACCESS_REFUSED configure access to queue 'cabinet.not-mine'` |
| `bindQueue(... platform.events, 'terminal.#')` | получилось |
| `publish` в `platform.events` | `403 ACCESS_REFUSED write access to exchange 'platform.events'` |

Консюмер контура **перезапущен** под суженными правами: поднялся, объявил
очередь, привязался и читает (`consumers = 1` на очереди, `RestartCount = 0`).

## Тег `administrator` был у продюсера

`site-web` заводился контейнером через `RABBITMQ_DEFAULT_USER`, а такой
пользователь получает тег `administrator` — то есть полный доступ к
management-API: чтение всех очередей, правка прав, заведение пользователей.
Кредл, чья единственная работа — публиковать одно событие, мог переписать права
самому себе.

Исправлено: заведён отдельный `bus-admin`, у `site-web` и `cabinet` теги сняты.
**Права AMQP и права management — разные механизмы**, и узкий `list_permissions`
ничего не говорит о том, что пользователь может через HTTP.

## Топология

```
                    platform.events  (topic, durable)
                            │
                            │  terminal.#
                            ▼
              cabinet.terminal-projection  (durable)
                            │
                            │  nack(requeue=false)
                            ▼
                  platform.events.dlx  (topic, durable)
                            │  #
                            ▼
            cabinet.terminal-projection.dlq  (durable)
```

DLX и DLQ объявлены владельцем шины, а не консюмером: консюмер только
ссылается на DLX параметром очереди и сам его не создаёт. **Если DLX не
существует, отбракованные сообщения молча исчезают** — брокер не считает это
ошибкой. До BUS-01 его не существовало.

## Чем проверено

Отказ **сначала воспроизведён**, потом закрыт.

> **Переподтверждено 06.10 (OPS-13).** Прогон 03.09 шёл против образов, которых
> больше нет: в консюмере с тех пор менялось поведение при невалидном
> сообщении (CON-01/CON-03), в релее — объявление обменника (REL-03). Решением
> Р-033 тот результат аннулирован. Таблица ниже — заново, на пересобранных
> образах (OPS-12) и под **суженными** правами `site-web`.

| Проверка | Результат |
| --- | --- |
| `site-web` объявляет обменник активно | `403` classId 40 — configure to exchange |
| `site-web` объявляет обменник пассивно | прошло (REL-03 сделал publish-only возможным) |
| `site-web` объявляет очередь | `403` classId 50 — configure to queue |
| `site-web` читает чужую очередь | `403` classId 60 — read to queue |
| `site-web` публикует | прошло, подтверждено брокером |
| Консюмер **с кредлом `site-web`** | `403` на `exchange.declare` — отказ воспроизведён |
| Консюмер с кредлом `cabinet` | `listening platform.events → cabinet.terminal-projection (terminal.#)` |
| Релей после перезапуска под суженными правами | `published_at` проставлен, `attempts = 0`, ошибок нет |
| Релей против несуществующего обменника | `404 NOT_FOUND`, обменник **не создан** |
| Чужое событие (`crm.lead.created` по ключу `terminal.#`) | `foreign event skipped: crm.lead.created <id> (foreign=1)`, `ack`, в DLQ **не** ушло |
| Сломанный конверт (`{}`) | `MALFORMED message → DLQ: envelope: event_id — Required (malformed=1)` → DLQ |
| Наш тип со сломанным payload | `MALFORMED message → DLQ: payload: terminal.account.opened id=<id> (malformed=2)` → DLQ, **event_id сохранён** |
| Сквозное: `terminal.account.opened` → БД | `applied`, `processed_events` 2 → 3, счёт `250000 USD` |
| Итог по очередям | `cabinet.terminal-projection` 0, `...dlq` 2 |

Последние строки и есть требование «кредл `site-web` по-прежнему не может
ничего, кроме публикации, — проверено попыткой», и требование «отказ сначала
воспроизвести, потом проверять починку».

**Чего эта таблица не доказывает.** Что отказ *записан там, где его будут
искать*: релей и консюмер падают необработанным событием `error` канала, и
строка `outbox` остаётся с `attempts = 0`, `last_error = NULL` (`B-OPS-006`).
Видно это только в логе процесса.

## CON-03 закрыт: проглоченное сообщение оставляет след

Раньше здесь стояло замечание в сторону OPS-09: невалидное сообщение
исчезало бесследно. В `apps/consumer/src/index.ts` стояло

```js
const event = parseMessage(raw);
if (!event) return; // не-терминальное/невалидное — молча пропускаем
```

и из трёх доставленных одно подтверждалось и терялось.

**Сделано командой `site-platform` (CON-03), в контуре с 06.10.** `parseMessage`
заменён на `classifyMessage` с размеченным результатом, и три исхода разведены:

| Что пришло | Что происходит теперь |
| --- | --- |
| не наш тип события | счётчик `foreign`, `console.debug` с именем события, `ack` — пропуск остаётся правильным |
| наш тип со сломанным payload | счётчик `malformed`, `console.warn` с причиной и `event_id`, событие в трекер, `throw` → `nack` → DLQ |
| сломанный конверт | то же, причина — `envelope: <поле> — <что не так>` |

Проверено публикацией всех трёх по очереди (таблица выше): различимы по логу,
по счётчику и по тому, где сообщение оказалось. Пропуск чужого события и
потеря своего перестали выглядеть одинаково — ради этого всё и делалось.
