# Шина событий · кредлы и права

Какие кредлы существуют, какие права у каждого и **почему именно такие**. Права
сужены осознанно: «дать всем всё» здесь не выход, потому что шина — общая для
платформы, и продюсер не должен уметь читать чужие очереди.

Локальная шина: RabbitMQ 3.13, vhost `platform`, AMQP 5672, консоль 15672.
Пароли — в `deploy/local/.env`, в историю не попадают.

## Кредлы

| Пользователь | Тег | configure | write | read |
| --- | --- | --- | --- | --- |
| `site-web` | нет | `^platform\.events$` | `^platform\.events$` | — |
| `cabinet` | нет | `^(platform\.events\|cabinet\.terminal-projection)$` | `^(cabinet\.terminal-projection\|platform\.events\.dlx)$` | `^(platform\.events\|cabinet\.terminal-projection(\.dlq)?)$` |
| `bus-admin` | administrator | `.*` | `.*` | `.*` |

## Почему у `site-web` есть `configure`, хотя он «publish-only»

Задача говорила: кредл `site-web` выдан publish-only, это правильно и менять не
нужно. **Проверено — в строгом виде это неверно, и релей от этого падает.**

Релей вызывает `assertExchange('platform.events', 'topic', {durable:true})`
перед первой публикацией. `exchange.declare` требует `configure` на обменнике
**всегда**, даже если обменник уже существует. С пустым `configure` релей
получает тот же `403`, что и консюмер:

```
ACCESS_REFUSED - configure access to exchange 'platform.events'
                 in vhost 'platform' refused for user 'site-web'
```

Воспроизведено: сузил права до пустого `configure`, перезапустил релей — он
ушёл в цикл падений (`RestartCount=3`), событие осталось в `outbox` с
`attempts=0`, то есть отказ произошёл **выше** пер-строчной логики повторов и
даже не записался как попытка публикации.

**Отказ отложенный, и это худшее в нём.** Пока у релея открыт канал, он не
переобъявляет обменник и работает. Сломается он только при следующем
переподключении — то есть при рестарте, разрыве сети или перезапуске брокера.
Сузь права в пятницу — узнаешь в понедельник.

Минимальное расширение: `configure` **только** на `^platform\.events$`. Этого
хватает релею и не даёт ничего лишнего: очередь объявить нельзя (проверено),
прочитать нельзя (проверено).

**Как сделать честный publish-only.** Релей должен объявлять обменник пассивно
(`checkExchange` вместо `assertExchange`), а сам обменник создаётся владельцем
шины один раз. Это правка в `apps/relay/src/publisher.ts`, то есть работа
команды `site-platform`, — вынесено штабу, здесь не делалось.

## Почему у `cabinet` есть `write` на DLX

Не догадка, а следствие отказа. Первый набор прав я вывел из задачи —
`configure` + `write` + `read` на очередь. Консюмер упал:

```
ACCESS_REFUSED - write access to exchange 'platform.events.dlx'
                 in vhost 'platform' refused for user 'cabinet'
```

RabbitMQ проверяет права на dead-letter-обменник **в момент `queue.declare`**, а
не когда сообщение реально отбраковывается. Очередь объявляется с
`deadLetterExchange: 'platform.events.dlx'`, и объявляющий обязан иметь `write`
на этот обменник. Ровно поэтому в постановке стояло «и её DLX».

## Откуда остальные права `cabinet`

Выведены из того, что консюмер делает, а не выданы про запас:

| Вызов в `subscriber.ts` | Требует |
| --- | --- |
| `assertExchange('platform.events')` | `configure` на обменнике |
| `assertQueue('cabinet.terminal-projection', {deadLetterExchange})` | `configure` на очереди + `write` на DLX |
| `bindQueue(queue, exchange, 'terminal.#')` | `write` на очереди (назначение) + `read` на обменнике (источник) |
| `consume(queue)` | `read` на очереди |

`read` на `cabinet.terminal-projection.dlq` добавлен сверх необходимого — чтобы
разбирать отбракованные сообщения тем же кредлом. Это осознанное расширение, не
упущение.

Как и у `site-web`, `configure` на `platform.events` нужен только из-за
`assertExchange`. Пассивное объявление сняло бы его и здесь.

## Тег `administrator` был у продюсера

`site-web` заводился контейнером через `RABBITMQ_DEFAULT_USER`, а такой
пользователь получает тег `administrator` — то есть полный доступ к
management-API: чтение всех очередей, правка прав, заведение пользователей.
Кредл, чья единственная работа — публиковать одно событие, мог переписать права
самому себе.

Исправлено: заведён отдельный `bus-admin`, у `site-web` и `cabinet` теги сняты.
**Права AMQP и права management — разные механизмы**, и узкий `list_permissions`
ничего не говорит о том, что пользователь может через HTTP.

## Топология

```
                    platform.events  (topic, durable)
                            │
                            │  terminal.#
                            ▼
              cabinet.terminal-projection  (durable)
                            │
                            │  nack(requeue=false)
                            ▼
                  platform.events.dlx  (topic, durable)
                            │  #
                            ▼
            cabinet.terminal-projection.dlq  (durable)
```

DLX и DLQ объявлены владельцем шины, а не консюмером: консюмер только
ссылается на DLX параметром очереди и сам его не создаёт. **Если DLX не
существует, отбракованные сообщения молча исчезают** — брокер не считает это
ошибкой. До BUS-01 его не существовало.

## Чем проверено

Отказ **сначала воспроизведён**, потом закрыт.

| Проверка | Результат |
| --- | --- |
| Консюмер с кредлом `site-web`, пустой `configure` | `403` на `exchange.declare` (classId 40, methodId 10) |
| Консюмер с кредлом `site-web`, `configure` на своём обменнике | `403` на `queue.declare` (classId 50, methodId 10) — **дословно та ошибка, что в задаче** |
| Релей под строгим publish-only | цикл падений, `RestartCount=3`, событие не опубликовано |
| Релей после минимального расширения | опубликовал, `published_at` проставлен |
| Консюмер с кредлом `cabinet` | `listening platform.events → cabinet.terminal-projection (terminal.#)` |
| Сквозное: `terminal.account.opened` → БД | `applied`, запись в `processed_events`, счёт в `demo_accounts` на 250000 |
| Сбойное событие (нет пользователя в `users`) | ушло в DLQ, в логе причина — FK-нарушение |
| `site-web` объявляет очередь | `403 configure access to queue` |
| `site-web` читает очередь, минуя объявление | `403 read access to queue` |

Последние две — и есть требование «кредл `site-web` по-прежнему не может ничего,
кроме публикации, проверено попыткой».

## Замечание в сторону OPS-09

Задача была про 403, но по дороге вскрылось, что **невалидное сообщение
исчезает бесследно**. В `apps/consumer/src/index.ts`:

```js
const event = parseMessage(raw);
if (!event) return; // не-терминальное/невалидное — молча пропускаем
```

Такое сообщение подтверждается (`ack`), в DLQ не уходит, в лог не пишется, в
GlitchTip не улетает. Замерено на счётчиках брокера: из трёх доставленных одно
`ack` — то самое, проглоченное, — и два `nack` в DLQ.

Пропускать неизвестное событие правильно: это дисциплина «потребитель парсит
мягко», без неё нельзя выкатывать части платформы порознь. Но «мягко» должно
значить «не падает», а не «исчезает без следа»: сегодня чужое событие и
собственное сломанное неотличимы. Достаточно счётчика и строки в лог.

Это правка в коде консюмера — команда `site-platform`. Здесь только зафиксировано.
