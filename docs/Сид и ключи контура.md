# Сид контура и ключи · OPS-11

Что лежит в локальном контуре в качестве данных, откуда это взялось, и какие
ключи где живут. **Значений ключей здесь нет и не будет** — репозиторий
публичный (Р-012). Здесь только имена переменных и место, где хранится значение.

## 1. Почему `pnpm seed` оставлял ноль строк

Вопрос в постановке стоял правильно: не «отработал ли с кодом 0», а **что
именно отработало**. Ответ: сид **выполнялся и падал на первом же действии**,
а код возврата 0 ставил не он.

Воспроизведено 05.10 на отдельной базе `seed_repro` (создана и удалена в тот же
заход, рабочие базы не затронуты), тем же образом `broker-local-cms-migrate`,
той же командой, что стояла в базовом компоузе:

```
sh -c "pnpm payload migrate && (NODE_ENV=production DEFAULT_SITE=apex-ru pnpm seed || echo 'seed skipped')"
```

Наблюдалось:

- `payload migrate` — три миграции применились, схема создалась целиком;
- `pnpm seed` — упал на `ensureUser` (`src/seed/index.ts:37`) с
  `ValidationError: The following field is invalid: Email`;
- `pnpm` вышел с кодом 1, `|| echo 'seed skipped'` подменил его на 0;
- **код контейнера 0**, `sites=0`, `users=0`.

Дифференциальная проверка на той же базе и том же образе: изменён ровно один
вход — `SEED_ADMIN_EMAIL`. Результат `sites=1`, `users=2`, контент и статьи на
месте. То есть причина — именно значение переменной, а не состояние базы,
не образ и не миграции.

**Причина значения.** `SEED_ADMIN_EMAIL` был `admin@localhost`. Payload требует
в адресе домен с TLD; `localhost` его не имеет. Адрес выглядит нормальным для
локального стенда и отвергается валидатором.

**Почему это не было видно.** Три слоя подряд превращали отказ в успех:

1. `|| echo 'seed skipped'` — код 1 становится кодом 0;
2. `cms-migrate` с кодом 0 удовлетворяет `service_completed_successfully`,
   и `cms` поднимается поверх пустой базы;
3. `/v1/health` CMS отвечает `{"status":"ok","db":"ok"}` на пустой базе —
   он проверяет соединение, а не наличие данных.

Наружу всё это выходило как `404 unknown_site` от выдачи — ответ,
неотличимый от «CMS не работает».

**Что сделано.** В `local/docker-compose.local.yml` у `cms-migrate` снят
`|| echo`: отказ сида теперь валит подъём контура. В `local/.env`
`SEED_ADMIN_EMAIL=admin@apex-ru.local` с комментарием, почему не `@localhost`.

**Урок.** Проверка состояния сервиса не является проверкой наличия данных, а
`||` в команде контейнера — это не «подстраховка», а стирание кода возврата.
Если шаг одноразовой джобы может провалиться осмысленно, он обязан валить
джобу; иначе `depends_on: service_completed_successfully` подтверждает не то,
что проверяет.

## 3. Ключи контура

Значения — только в `deploy/local/.env`, он закрыт `.gitignore`
(`.env`, `.env.*`). В историю ничего из этого не попадает.

| Переменная | Кто потребляет | Состояние |
| --- | --- | --- |
| `CMS_API_KEY` | `cms` (проверяет), `web`, `cabinet`, терминал (шлют `X-API-Key`) | задан, 32 символа |
| `SSO_PRIVATE_KEY_B64` | `cabinet` → `/api/sso/jwks` | задан, RSA-2048 PKCS#8, `kid=platform-sso-1` |
| `PAYLOAD_SECRET`, `CMS_WEBHOOK_SECRET`, `PREVIEW_SECRET` | CMS | заданы |
| `SITE_DB_PASSWORD`, `CMS_DB_PASSWORD`, `BUS_PASSWORD` | базы и шина | заданы |
| `TWELVEDATA_API_KEY` | MDS | **пуст** — вселенная только Binance |

### SSO: пара сгенерирована деплоем, а не `site-platform`

По постановке пару генерирует команда `site-platform`. Её не было, контур стоял.
Пара сгенерирована здесь 09.09 **только для локального контура**: RSA-2048,
PKCS#8, base64 одной строкой. Публичная половина нигде не хранится — кабинет
выводит JWK из приватного ключа и отдаёт на `/api/sso/jwks`.

Это ключ разработки. Боевая пара обязана быть сгенерирована владельцем ключа и
**не может** быть этой: она лежала в окружении машины, на которой идёт
разработка пяти команд. Записано как `TD-OPS-004`.

### Выдача `X-API-Key` терминалу

Ключ один на контур (`CMS_API_KEY`) и уже работает: `cms` принимает его на
`/v1/cms/*`. Терминалу он передаётся **значением через штаб**, а не файлом в
их репозитории: `terminal/` — чужая папка, и запись в неё за пределами зоны
`deploy`. Переменные на их стороне — `CMS_BASE_URL` и ключ для заголовка
`X-API-Key` (см. `terminal/.env.example`, раздел allow-list).

**Ключ не является решением их задачи целиком** — см. раздел 4.

## 4. `terminalInstrumentId`: поля нет в схеме

Отдельный вопрос штаба. Ответ: **поле не заполнено, потому что его не
существует** — ни в карточке сайта, ни где-либо ещё в legacy-CMS.

Проверено тремя независимыми способами:

- поиск по схеме базы: во всём `public` есть ровно два подходящих столбца —
  `sites.instruments :: jsonb` и `payload_locked_documents_rels.site_instruments_id`.
  Столбца с `terminal` в имени нет ни одного;
- поиск по исходникам `cms-legacy`: вхождений `terminalInstrumentId` ноль;
- `src/collections/Sites.ts`: `instruments` — поле типа `json` без схемы,
  подписанное «доступ сайта к вселенной MDS», с кастомным редактором
  `MdsAllowListField`.

Выдача подтверждает: `src/app/v1/cms/[...path]/route.ts` отдаёт
`instruments: site.instruments.map(String)` — **плоский массив строк-символов**.

Чего ждёт терминал (`backend/gateway/src/lib.rs`, `.env.example`):
`HashMap<String, Vec<u32>>`, то есть **числовые** id, формат
`site:id,id;site2:id`. Между «массив строк `BTCUSD`» и «массив чисел» нет
преобразования — это не пустое поле, это другая форма ответа.

Статус у соседей совпадает: в `site-platform/docs/Задачи.md` строка
`terminalInstrumentId в CMS instruments` стоит невыполненной с пометкой «ЖДЁТ
ответа терминала».

### Чем это опасно прямо сейчас

Пустой allow-list читается **тремя потребителями по-разному**, и ни один не
сообщает об этом наружу:

| Потребитель | Что делает с `instruments: []` | Видно ли |
| --- | --- | --- |
| `web` (`apps/web/lib/tenant.ts`) | `length === 0` → `null` → **граница снята**, показывает весь контент | нет |
| `cabinet` (`apps/cabinet/lib/tenant.ts`) | `new Set([])` → фильтр не пропускает ничего → модуль «Рынки» возвращает `null` и **исчезает со страницы** | нет |
| `terminal` | `None` → **торговля закрыта** (fail-closed, КОНТРАКТЫ §4б) | да, отказом |

То есть одно и то же значение на одной и той же границе доступа означает
«всё разрешено», «ничего нет» и «торговля запрещена». Плюс `web` не отличает
«список не настроен» от «CMS недоступна» — обе ветки дают `null` и обе
деградируют **открыто**, на границе доступа, заведённой ради регуляторики
(ADR-028).

Записано как `B-OPS-002`.

## 5. Витрина обещает 33 инструмента, котировки есть у 6

Побочная находка того же разбора. Каталог CMS для `apex-ru` — 33 символа.
Вселенная MDS — 501 символ, все от Binance. Пересечение — **6**:
`BTCUSD`, `ETHUSD`, `BNBUSD`, `XRPUSD`, `SOLUSD`, `EURUSD`.

Остальные 27 — форекс, металлы, индексы, акции (`XAUUSD`, `US500`, `AAPL`,
`USDJPY` и прочие) — в MDS отсутствуют, потому что `TWELVEDATA_API_KEY` пуст
(сознательно, OPS-02). Их страницы на витрине открываются и живых котировок не
получают.

Сегодня это не бросается в глаза ровно потому, что allow-list пуст и граница
снята. **Как только allow-list будет заполнен чем угодно, витрина покажет 6
инструментов вместо 33** — независимо от того, положить туда пересечение или
всю вселенную MDS: `web` фильтрует контент CMS по списку, а в контенте всего
33 символа.

Поэтому allow-list **намеренно оставлен пустым** в этом заходе: его содержимое —
продуктовое и регуляторное решение, а его включение заметно меняет витрину.
Решение за штабом.

Варианты, оба обратимы, оба выполняются в `cms-legacy`:

```sh
# А. Вся текущая вселенная MDS (501), штатный путь ADR-027
pnpm payload run scripts/backfill-allow-list.ts

# Б. Только то, что одновременно в каталоге и в MDS (6) — задаётся
#    в админке CMS, карточка сайта apex-ru, поле «Инструменты сайта»
```
