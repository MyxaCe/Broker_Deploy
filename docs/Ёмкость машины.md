## Освобождение внутри Docker места хосту не отдаёт

```
> fsutil sparse queryflag docker_data.vhdx
This file is NOT set as sparse
> compact /q docker_data.vhdx
41 582 329 856 total bytes of data are stored in 41 582 329 856 bytes.
```

Файл занимает ровно свой логический размер: дыр нет, 38,73 ГБ выделены целиком.
`docker system prune` освободит место **внутри** ext4 виртуальной машины, а
`docker_data.vhdx` на `C:` останется прежним.

Чистить всё равно нужно, но по другой причине: освобождённое внутри
переиспользуется новыми слоями, и `vhdx` **перестаёт расти**. Растёт он сейчас
за счёт тех самых 18,9 ГБ — каждая сборка контура без чистки отъедает их
напрямую. Чистка внутри = сборки контура не трогают хост.

Чтобы вернуть место именно Windows, нужен отдельный шаг: сжатие диска ВМ
(`wsl --manage docker-desktop --set-sparse true` либо остановка Docker Desktop и
`diskpart compact vdisk`). Это операция над диском с данными пяти чужих
проектов — **вопрос штабу, молча не делаю**.

## Реклейм: 5 ГБ, а не 11

Замер на 11:40 (числа живые, за час менялись дважды):

```
TYPE            TOTAL   ACTIVE   SIZE      RECLAIMABLE
Images          35      27       20.15GB   6.771GB (33%)
Containers      37      20       250.4MB   26.08MB (10%)
Local Volumes   25      18       4.333GB   2.555GB (58%)
Build Cache     237     0        15.18GB   4.952GB
```

Цифра штаба «образы 20,15 / реклейм 6,77» воспроизведена — она верна. Неверен
вывод, что эти 6,77 ГБ поднимаются `docker image prune` без вреда.

**Висячих образов ноль** (`docker images -f dangling=true` — пусто). Значит
`docker image prune` освободит **0 байт**. Все 6,77 ГБ — это образы с тегами, и
достать их можно только через `docker image prune -a`, который удаляет всё, что
не занято **запущенным** контейнером. Под нож попадут:

- 7 образов `mica-v2` (~1,4 ГБ) — dev-копия CRM, прямо вне нашей зоны;
- `rust:slim` (1,27 ГБ) — им пересобирается гейтвей терминала;
- `node:22-alpine`, `node:20-alpine`, `python:3.12-slim` — базовые образы,
  на которых **наш же контур и собирается**. Удалить, чтобы через час
  выкачивать заново;
- `playwright` (3,47 ГБ) — чей-то прогон e2e.

То есть `-a` — это не «без единого согласования и без риска», а наоборот:
задевает три чужих проекта и вредит нашей же следующей сборке.

**Что действительно безопасно:**

| Действие | Вернёт внутри Docker | Риск |
| --- | --- | --- |
| `docker builder prune -f` (без `-a`) | **4,95 ГБ** | нет: удаляются только записи кеша, которые уже ничем не шарятся |
| `docker image prune -f` | 0 ГБ | нет, но и пользы нет — висячих нет |
| удалить **поимённо** четыре наших образа (ниже) | **2,35 ГБ** | нет: наши, контейнеров нет |
| **итого** | **≈ 7,3 ГБ** | |

`docker builder prune -a` вернул бы все 15,18 ГБ, но заставил бы пересобираться
с нуля все пять проектов. Не предлагаю.

## Бюджет под контур

Безопасно освобождается **≈ 7,3 ГБ** внутри Docker. Хосту — ноль, пока не сжат
`vhdx`.

Сколько нужно контуру — **оценка, не факт**: девять сервисов, шесть собираются.
По уже существующим образам (`cms` 408 МБ, `web` 291 МБ, `relay` 475 МБ,
build-stage CMS 2,09 ГБ) холодная сборка встанет примерно в **8–10 ГБ** вместе
с кешем. Точное число измеряется в OPS-02 замером `df` до и после; до тех пор
называть его фактом нельзя.

7,3 ГБ против оценки 8–10 ГБ — впритык или чуть-чуть не хватает. Недостача
полезет в 18,9 ГБ хоста через рост `vhdx`. **Поэтому сжатие `vhdx` — не
косметика, а условие OPS-02.**

### Свободное место на `C:` не выросло — как и было предсказано

| | До | После |
| --- | --- | --- |
| `C:` свободно | 18,9 ГБ | **18,4 ГБ** |
| `docker_data.vhdx` | 38,73 ГБ | **38,73 ГБ** |

Девять с половиной гигабайт освободились внутри ВМ, файл диска не сдвинулся ни
на мегабайт. Свободного места на хосте стало **меньше** — полгигабайта ушло на
работу соседних команд за те же минуты.

Это больше не предсказание из свойств `vhdx`, а измеренный факт. Вывод в силе и
усиливается: **чистка Docker не лечит диск машины.** Она делает другое, и это
тоже нужно — теперь у контура есть 9,68 ГБ внутри ВМ, и его сборка не будет
отъедать хостовые 18,4 ГБ ростом `vhdx`. Против оценки в 8–10 ГБ на холодную
сборку этого уже хватает.

### Побочное следствие, о котором надо знать

Удалив пять контейнеров, я снял последние ссылки с наших томов
`broker_cms-main_pgdata` (76,1 МБ), `sait_platform-main_db-data` (48,3 МБ) и
`broker_cms-main_cms-media`. Сами они целы, но теперь их снесёт любой
`docker volume prune -f`, запущенный кем угодно на этой машине. Защищавшая их
ссылка исчезла как раз потому, что контейнеры были мёртвыми.

Это не аргумент против чистки — это аргумент за OPS-04 и повод предупредить
соседей: **`docker volume prune` на этой машине сейчас опасен.**
