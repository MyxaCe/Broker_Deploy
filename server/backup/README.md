# Бэкап стенда · OPS-04 (веха 5)

Снимок состояния платформы на сервере: `backup.sh` снимает, `restore-check.sh`
проверяет восстановлением. Обе гоняются по расписанию systemd
(`broker-backup.timer` 02:30 UTC, `broker-restore-check.timer` 03:30 UTC), а не
«когда понадобится». Назначение снимков — `/var/backups/broker/<снимок>`,
хранится `KEEP=7` последних.

**Эти файлы до 01.11 не были в репозитории вообще** — жили только на машине,
хотя `server/README.md` объявляет содержимое репозитория источником правды.
Это та же дыра, что закрывает сам бэкап, этажом выше: конфигурация бэкапа
существовала в одном экземпляре. Теперь она здесь.

## Что резервируется

| Что | Как | Почему так |
| --- | --- | --- |
| базы `broker_cms`, `broker_site`, `terminal` | `pg_dumpall` + опись строк на момент снимка | копировать каталог живой Postgres нельзя; опись превращает «что-то восстановилось» в «то же самое» |
| **том `broker-site_minio-data` (KYC)** | `tar` одноразовым alpine, том только на чтение, + опись (число файлов и свёртка) | **KYC-документы, срок хранения 5 лет**; дамп их не видит, `config.tar.gz` берёт только `/srv/broker` |
| тома `broker-site_cabinet-uploads`, `broker-cms_media` | то же | файлы, которых нет ни в базе, ни в репозитории |
| `/srv/broker` целиком | `config.tar.gz` | конфигурация всех служб (включает `.env` — см. ниже) |

## Две находки веха-5 (01.11), ради которых правка и сделана

### 1. KYC (MinIO) был ВНЕ бэкапа

Том `broker-site_minio-data` не резервировался ничем: это не Postgres (дамп
его не берёт), а данные лежат в томе Docker, а не в `/srv/broker` (куда смотрит
`config.tar.gz`). Критичные данные с пятилетним сроком хранения существовали в
одном экземпляре. Закрыто: том снимается `tar`, и `restore-check` проверяет,
что из архива восстанавливается ровно то, что снято (сверка с описью снимка, а
**не** с живым томом — живой за час между снимком и проверкой мог принять
новые документы, и сверка с ним краснела бы не по делу).

### 2. Фильтр баз молча ронял ВСЕ три дампа

Первая редакция искала базы по колонке `docker ps --format '{{.Image}}'` и
подстроке `postgres`. Эта колонка печатает **ид-хеш**, когда тег образа
отвязан от запущенного контейнера. 01.11 при выкатке MinIO так и вышло: три
базы на `postgres:16-alpine` показались как `f461079…`, фильтр их не нашёл, и
снимок 02:30 ушёл **без единого дампа**. `restore-check` в 03:30 это поймал
(вышел с кодом 2 — «дампов нет»), но сам снимок был пуст. Исправлено: образ
читается из `docker inspect -f '{{.Config.Image}}'` — там хеш не подставляется,
«образ не врёт» на деле, а не на словах.

## Охват томов объявлен числом

Списки томов ведутся руками, и новый том иначе не попал бы в снимок молча —
ровно тот отказ, против которого всё и написано. `backup.sh` берёт список
томов из Docker и сверяет с тремя списками: `VOL_ARCHIVE` (архивируются),
`VOL_BY_DUMP` (покрыты дампом БД), `VOL_COVERED_OTHERWISE` (восстановимы без
архива, с записанной причиной у каждого). Том вне всех трёх — снимок считается
**неполным** (код ≠ 0), хотя каталог уже создан: частичный снимок лучше
никакого, но зелёным не зовётся.

## Чего этот бэкап НЕ закрывает (честно)

- **Снимок лежит на той же машине** (`/var/backups/broker`). От потери диска
  частично спасает, от потери доступа к машине — нет. Внешняя копия — открытая
  строка, решение владельца (см. `docs/Бэкапы.md`, раздел про внешнюю копию).
- **`config.tar.gz` содержит `.env` всех служб** (секреты, права 600). Для
  снимка на той же машине это приемлемо, но из этого следует: снимок **нельзя**
  выносить наружу незашифрованным. Целевой дом секретов — Vault
  (`server/СЕКРЕТЫ-Vault-спека.md`); после переезда в снимок поедут
  зашифрованные данные Vault, а не открытые `.env`.
- **Пустые тома** (`cms-media` сегодня) проверены только механизмом, не на
  данных: появятся файлы — строка ПУСТО уйдёт сама.

## Запуск вручную

```bash
/srv/broker/backup/backup.sh          # снять снимок
/srv/broker/backup/restore-check.sh   # проверить последний
```
