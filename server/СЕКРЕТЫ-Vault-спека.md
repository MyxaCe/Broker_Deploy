# Хранилище секретов (Vault) — спека, готовая к исполнению

Статус: **ратифицировано как цель** (см. `site/.env.example`: «Целевой дом
ключей — Vault»), но **живой Vault НЕ поднят**. Этот документ — пошаговый
план; он ждёт одной отмашки владельца и трёх его решений (в конце). Ничего из
этого не выполнено на машине.

## Зачем вообще

Сегодня секреты лежат в `*.env` каждой службы, права `600`, владелец `root`.
`server/README.md` называет это прямо: **это не хранилище секретов, а отсрочка
с названной ценой** — ротации нет, журнала доступа нет, кто читал — неизвестно.
Отдельно: пароли контура когда-то лежали в репозиториях и потому **считаются
скомпрометированными** — то есть переезд в Vault обязан сопровождаться
ротацией, а не просто копированием значений.

## Что именно поднять

- **HashiCorp Vault**, один узел, хранилище `raft` (integrated storage — не
  требует внешней БД), образ запинен по дайджесту (как MinIO и всё на стенде,
  OPS-23). Dev-режим (`-dev`, без печати) **запрещён**: он держит всё в памяти
  и не запечатывается.
- Сеть `broker-back`, **портов наружу нет** (как у всех служб, кроме прокси).
  UI/API доступен только изнутри; наружу — отдельным решением штаба через
  прокси с тем же заслоном по адресу источника, что у CMS (`ADMIN_IP`).
- Том `vault-data` (raft) — **добавить в `VOL_ARCHIVE` бэкапа** (данные в нём
  зашифрованы; ключи распечатывания в бэкап НЕ попадают — их держит владелец,
  см. решение 1).
- Capability `IPC_LOCK` (чтобы Vault не свопил ключи на диск).

## Какие секреты переезжают и куда

KV v2, путь на службу — чтобы политика резалась по префиксу:

| Путь в Vault | Что лежит | Источник сегодня |
| --- | --- | --- |
| `secret/site/*` | `SITE_DB_PASSWORD`, `CMS_WEBHOOK_SECRET`, `PREVIEW_SECRET`, `CMS_API_KEY`, `ADMIN_SESSION_SECRET` | `site/.env` |
| `secret/site/sso` | **`SSO_PRIVATE_KEY_B64` — приватный ключ подписи handoff-JWT (денежный путь, Р-452)** | `site/.env` |
| `secret/kyc/*` | `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_BUCKET` (ADM-12 / Р-454) | `site/.env` |
| `secret/cab/*` | **будущие кошельки CAB-13** | ещё не существуют — путь резервируется |
| `secret/monitoring/*` | `GRAFANA_PASSWORD`, по готовности `TG_*`/`MAIL_*` | `monitoring/.env` |

### Ключ подписи денег (Р-452) — два варианта, и выбор за владельцем+разработкой

1. **Interim (без правки приложения):** ключ лежит в KV (`secret/site/sso`),
   Vault Agent отдаёт его в `.env` как сейчас. Защищает хранение и ротацию, но
   ключ всё равно в момент работы живёт в памяти приложения.
2. **Target (правка приложения):** Vault **Transit** — приложение просит Vault
   *подписать*, ключ **никогда не покидает Vault**. Это решение 3 ниже: нужна
   работа команды витрины (вызов Transit вместо локальной подписи).

Начинаем с (1) — он закрывает «секрет в открытом файле» сегодня; (2) —
следующим заходом, когда разработка подпишется.

## Как службы будут читать

Минимальная правка существующего контура: **Vault Agent как sidecar на стек**.
Agent логинится по **AppRole** (своя роль на стек, политика только на свой
префикс — least privilege), берёт секреты из Vault и **рендерит тот же `.env`**,
который `compose.sh` уже читает. То есть механизм доставки секретов меняется, а
`compose.sh` и сами приложения — нет (кроме Transit-варианта для Р-452).

```
Vault  ──AppRole(site)──►  vault-agent(site)  ──template──►  site/.env.vault
                                                             │
                                                 compose.sh читает ─┘ (как сейчас)
```

Роли и политики:

| AppRole | Политика (чтение) |
| --- | --- |
| `site` | `secret/site/*`, `secret/kyc/*` |
| `monitoring` | `secret/monitoring/*` |
| `cab` (будущее) | `secret/cab/*` |

## Пошаговый план (по отмашке)

1. `server/vault/compose.yml` + `config.hcl` (raft, listener без TLS внутри
   `broker-back` либо mTLS — решение штаба), образ по дайджесту, том
   `vault-data`, `IPC_LOCK`, без `ports:`.
2. `vault operator init` → **5 ключей распечатывания + root-токен**. Выдать
   владельцу out-of-band (решение 1). Распечатать (`vault operator unseal`).
3. Включить `secret/` (KV v2); при выборе target — `transit` и ключ подписи.
4. Залить текущие значения из `*.env` в соответствующие пути.
5. Создать политики + AppRole на стек, выдать `role_id`/`secret_id` агентам.
6. Добавить `vault-agent` в каждый стек, рендер `*.env.vault`, переключить
   `compose.sh` на него.
7. **Ротировать** все секреты, что когда-либо были в git/env (скомпрометированы):
   пароли БД, `CMS_API_KEY`, `ADMIN_SESSION_SECRET`, ключи MinIO; перевыпустить
   ключ подписи Р-452 (с окном двойной проверки подписи на стороне терминала).
8. Добавить `vault-data` в `VOL_ARCHIVE` бэкапа.
9. **Проверка срабатыванием:** служба стартует, читает секрет из Vault; затем
   запечатать Vault и показать, что служба без него не стартует (а не «вроде
   читает»). Распечатать обратно.

## Что нужно от владельца

1. **Отмашка поднять Vault** (это новый долгоживущий сервис с хранилищем).
2. **Кто держит ключи распечатывания** (5 ключей Шамира) и root-токен, и
   **где офлайн**. Это курица-и-яйцо хранилища секретов: сам ключ от хранилища
   где-то жить обязан, и это не машина (иначе Vault бессмыслен). Без ответа
   Vault нельзя распечатать после перезагрузки — а значит и поднимать рано.
3. **Р-452: KV (interim) или Transit (target)?** Transit требует правки
   команды витрины. По умолчанию берём KV, Transit — следующим заходом.
4. (не блокирует) Выводить ли UI Vault наружу через прокси под `ADMIN_IP`, или
   оставить только CLI/API изнутри.

## Что можем сами (без владельца)

- Написать `server/vault/compose.yml`, `config.hcl`, политики и роли —
  **файлами, с плейсхолдерами**, не поднимая Vault.
- Написать шаблоны Vault Agent и правку `compose.sh` (за флагом, выключено).
- Подготовить процедуру ротации всех скомпрометированных секретов.

Секреты в репозиторий не коммитятся: здесь только имена путей и плейсхолдеры.
